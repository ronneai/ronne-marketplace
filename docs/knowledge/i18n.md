# Languages: how the web app's text is kept

The web app speaks English (the source), Brazilian Portuguese (`pt`) and Canadian French (`fr`)
([feature 129](../features/129-languages-foundation/SPEC.md)). Only the platform's own labels are
translated: item content, what people write, `rmk`, the MCP server and the API stay as authored.
Read this before writing any text a person reads on a screen.

## Where text lives

- **`apps/web/messages/<locale>/<namespace>.json`**, one file per area (`common`, `shell`, …), the
  same keys in all three languages. English is the source: write it first, then the other two.
  A new namespace adds its three files and a line in `src/i18n/namespaces.ts` (also its type).
- **ICU messages** for anything with a number or a name: `{count, number}`, `{count, plural, one {…}
  other {…}}`, `{role, select, …}`. Whole sentences with placeholders, never fragments that are
  joined in code. Plural categories differ by language; `other` is always required.
- **In components:** `const t = useTranslations("shell")` then `t("nav.home")` (a non-async server
  component or a client component), or `await getTranslations("shell")` in an async server
  component. Keys are typed from the English files: a wrong key fails `pnpm typecheck`.
- **In tests:** components render in English (`src/test/intl-setup.ts` reads the real files). A
  test of another language wraps the render: `inLocale("pt", () => renderToStaticMarkup(…))`.
- **Never** write text into JSX or a `title`/`label`/`placeholder`/`aria-label`/`alt`/
  `description`/`summary`/`heading`/`tooltip` attribute in a folder the lint rule covers (the
  `overrides` entry in `biome.json` that loads `i18n-raw-jsx-*.grit`). A string that isn't
  translated text (a brand name, a protocol) carries `// biome-ignore lint/plugin: <why>`. A folder
  joins the list when its screens are moved over; text the rule can't see (default parameters,
  template strings, objects) is on the author and the reviewer.

## Errors

- **An action that returns a code** (`{ error: "wrong_password" }`): the component turns the code
  into words with a key in its own messages (`account.password.errors.wrong_password`). The code
  stays the contract; the words are the screen's.
- **A domain error with a message** (`TokenLimitError`, 152 more): the action returns
  `await errorText(error)` (`src/i18n/errors.ts`). It looks up `errors.<ClassName>` in the
  `errors` namespace with the error's own fields as the message's values (`{limit}`,
  `{tokenName}`), and falls back to the error's English message, so a new error is never blank,
  only English until someone translates it. The API keeps giving the English message and its code.
  A sweep adds the errors its screens can show, in all three languages; a test per error class
  checks the three texts (`src/i18n/errors.test.ts`).

- **A message the server builds from several steps** (the setup wizard's, feature 132): keep the
  English `message` for the API and the tests, and add a `say` beside it (`{ key, values }`, a key of
  `admin.setup.errors` or `.detail`); the screen words it with `useSay` and shows the English when
  there is no `say` (a driver's own text, the database check's explanation). Text from `server/`,
  from a driver or from the identity domain's presets stays English and is named in the feature's
  spec.

## Checks that keep it true

- `src/i18n/messages.parity.test.ts`: every key of English in `pt` and `fr`, no extra key, the same
  ICU placeholders, valid ICU.
- At run time a missing message shows English (and is logged once); CI fails on it.
- The lint rule above, tested on fixtures in `src/i18n/raw-text.test.ts`.

## Gotchas

- **A test that scans a page for English** (`englishLeaks`, the e2e `noEnglish`) skips a message
  that is identical to its English one, and a message in another key's English. The guards for that
  are `src/i18n/*-untranslated.test.ts` (pt and fr text equal to the English fails, with a SAME
  table for the words that really are the same). A pt or fr text that is *part* English is caught
  by none of them: the native review reads them. The e2e scan splits the text on newlines **and
  tabs**, because a table row is tab-joined.
- **The English-words check** (`src/i18n/english-fragments.test.ts`, 133): a pt or fr message with
  an English word from its list (function words such as "the" and "with", and product words such as
  "user", "workspace", "settings") fails unless `english-fragments.allow.json` has the message with a
  reason (a quoted provider screen, a command, an example name). **Its limit:** an English word that
  is not on the list is not seen, so a half-translated message with other English nouns or verbs
  ("saved" was one) passes until it is added to the list; the native review (133) is what reads the
  rest. A word that is also a real Portuguese or French word ("but", "more", "are") must not go on
  the list.
- **The native-speaker review kit** (133): `pnpm i18n:review` writes every message, English beside
  Portuguese and French, with the glossary and the website's pages, to a git-ignored folder under
  `docs/features/133-languages-signoff/review/`; `REVIEW-GUIDE.md` there tells a reader what to
  look at, and `REVIEW.md` records what became of each finding. A correction is made in the
  message file, then the export is run again.
- **The Documentation links** (133): `pnpm docs:links` compares the app's topics and sections with
  the website's (`../ronne-web`) and `--live` opens every page on the deployed site. A topic or
  section added or renamed on one side is changed on the other, in the same release.
- **The inline helpers** (`Help`) have no text in `Help.tsx`: `help.<id>.question` and `.answer`
  in the three languages, and only the link in `HELP`.
- **ICU and angle brackets:** a message with a literal `<` (such as `deleted-user-<id>`) writes it
  quoted, `'<'id'>'`; a tag (`<code>…</code>`) needs a `t.rich` handler.

- After adding a **new namespace** (a message file registered in `src/i18n/namespaces.ts`), Vitest can
  fail every test with `Unknown variable dynamic import: ../../messages/en/<file>.json`: its cache
  holds the old file list. Delete the caches (`node_modules/.vite*` and `node_modules/.vitest-cache`,
  at the root and in `apps/web`, whichever exist) and run again. A new key in an existing file is
  fine.
- Timestamps keep one numeric form in every language (`2026-10-20 21:58 GMT-4`, 049); only numbers
  (`12,345` / `12.345` / `12 345`) follow the language.
- E2E: a test that needs several languages signs in once and opens the same session with
  `browser.newContext({ locale, storageState })`, with a user of its own (the sign-in limit,
  [e2e-sign-in-limit.md](./e2e-sign-in-limit.md)).

## Adding a message, a screen's worth, or a language

- **A message:** its key in all three `messages/<locale>/<namespace>.json` (English first), used
  through `useTranslations`; run `pnpm exec vitest run src/i18n` for parity and placeholders.
- **A new screen (since 133):** the lint rule already covers it (the whole of `apps/web/src`,
  bar the server, the API and the styleguide); move its text, its error maps (a code becomes a
  key) and the domain errors it can show (`errors.json`); add the page to `SWEEP_PAGES` in
  `e2e/pages.ts` (the coverage test fails until it is there) and the phone sweep runs it in all three
  languages; a test per area in three languages, with the English-leak guard (see
  `features/account/translations.test.tsx`); the glossary above for any new term; the Portuguese
  and French pages of the Documentation take the new names of the labels they mention.
- **A language:** a folder `messages/<code>/` with every namespace (the parity test fails until it
  has them all, and until the folder list equals `LOCALES`); the code in `LOCALES` and its own name
  in `LOCALE_NAMES` (`models/locale.ts`); the website first, since the Documentation links
  (`localizedDocsHref`, typed by `Locale`) need its pages. In ronne-web the edits are
  `src/i18n/routing.ts`, `www/messages/<code>.json`, `src/content/docs/<code>/` and the
  `ogLocales` map in `src/lib/metadata.ts`; its language switcher and sitemap follow
  `routing.locales` by themselves. The `Accept-Language` matching,
  the Language form and the sign-in links follow `LOCALES` by themselves. The `CASES` of
  `e2e/languages.e2e.ts` and the language of `e2e/languages.mobile.e2e.ts` and the sweep's
  `LANGUAGES` (`e2e/mobile-sweep.mobile.e2e.ts`) get an entry. Add it to the glossary and the
  typography notes here.

## Typography

- **Portuguese (Brazil):** no space before `: ; ? !`.
- **French (Canada):** a space before a colon `:` only, none before `; ? !` (the Canadian rule, as the
  website's translation guide has it; the French of France puts one before all four), the curly
  apostrophe `’` in the app (`s’ouvre`, `Journal d’audit`; the website's prose keeps the straight
  one, a difference of glyph only), « guillemets » with a space inside for quotes. The spaces are
  regular ones for now.
- Both: no gendered address of the person; "you" as `você` / `vous`.
